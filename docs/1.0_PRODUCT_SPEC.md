# BloomOS 1.0 Product Specification

Status: normative for 1.0 development. Last updated: 2026-08-22.

## Product promise

BloomOS is a fast, open, recoverable gaming appliance for the Miyoo Mini V1-V4,
Mini Plus, and Mini Flip. Version 1.0 replaces the normal closed MainUI path with
a Bloom-owned shell while preserving the proven launch, session, save, update,
rollback, and Onion migration boundaries.

The priorities, in order, are protecting user data, launching and resuming games
quickly, understandable interaction, responsiveness, recoverable failure,
consistent device behavior, useful Onion compatibility, bounded background work,
and minimal dependencies.

## Supported 1.0 experience

- Boot to a Bloom-owned root launcher and resume the latest game with `A`.
- Open Games, Favorites, Recent, Apps, and Settings directly without MainUI.
- Launch through structured Bloom requests using canonical Bloom GameID.
- Return from games and apps directly to Bloom Shell.
- Use one owner for settings, favorites, recents, activity, and library state.
- Inspect health, install signed updates, confirm, and roll back without MainUI.
- Recover with a default-theme, optional-service-free Safe Mode whose guarded
  Settings reset preserves user games, saves, states, library/history data, and
  account credentials.
- Work fully offline; network and RetroAchievements failures never block play.
- Complete migration through one recoverable first-run welcome surface that
  preserves imported settings, games, saves, states, library, and history.

The stable release does not include cloud saves, profiles, Kids Mode, a package
marketplace, Nearby Play, broad scraping, Nintendo DS, unrelated handhelds, or
uncertified offline RetroAchievements awards.

## Non-negotiable contracts

- Bloom GameID is canonical and launch requests remain structured.
- A clean session is reported only after scoped save flush succeeds.
- Snapshots and update rollback remain recoverable and provenance fails closed.
- ROMs, BIOS, saves, credentials, hashes, titles, and private paths stay out of
  normal health and support exports.
- Permanent RetroArch configuration is not a per-session policy channel.
- Migration never destroys the only copy of user-owned data.
- First-run completion is published only after canonical Bloom settings
  authority is active; interrupted or malformed state remains retryable.
- Hardware is called verified only when the required physical evidence exists.
- MainUI fallback may exist only behind an explicit Developer Mode recovery
  gate until replacement is fully certified; normal boot and Bloom Safe Mode
  do not depend on it.
- Bloom-owned UI navigation requires no shoulder buttons. Stable Bloom Shell
  assigns L1, L2, R1, and R2 no navigation role; MENU means GameSwitcher and
  START means Quick Settings.
- Normal hierarchy is root, primary screen, and at most one focused detail or
  action layer. Stable Settings is flat and sectioned rather than a menu tree.

## Release gates

Stable 1.0 requires the architecture, branding, UX, reliability, hardware, and
release checks in [the test matrix](1.0_TEST_MATRIX.md). In particular: no known
save-loss or filesystem-corruption bug; no open P0/P1; green Safe Mode and
automatic update rollback; a responsive 10k-game fixture; bounded shell memory;
and honest physical evidence for V2, Plus, Flip, and external V1/V3/V4 claims.

The release candidate process is Alpha (Bloom Shell development default), Beta
(Bloom Shell default with recovery-only fallback), RC1 (feature freeze), later
RCs (release blockers only), then stable after every mandatory gate is recorded.

## State ownership target

| State | 1.0 authority | Import/compatibility boundary |
|---|---|---|
| Global and device settings | `bloom-settings` | `system.json` and Onion flags |
| Games, systems, apps | `bloom-library` | Onion configs and ROM layout |
| Favorites and recents | Bloom library/activity stores | Onion JSON/list import |
| Launch and active session | Bloom launch/session services | `cmd_to_run.sh` adapter only |
| Saves and states | Emulator files plus Bloom durability/snapshots | Existing Onion layout |
| Power and network | Bloom platform services | Firmware-specific adapters |
| Update lifecycle | Bloom signed updater | Firmware boot trigger adapter |

Historical Onion attribution remains in source, licenses, migration, and
compatibility documentation. It is not product branding.
